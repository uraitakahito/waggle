## What waggle is

waggle answers one question: **which URLs get captured**. It selects the enabled
rows of a Postgres `urls` table and submits one `SubmitCapture` call per row to a
BrowserHive server, in parallel.

The name comes from the [waggle dance](https://en.wikipedia.org/wiki/Waggle_dance)
bees use to point hive-mates at nectar.

## What is not waggle's responsibility

Driving a browser, taking screenshots, building a WACZ, writing to S3 — every
one of those is **BrowserHive's responsibility**. Not a gap waggle has yet to
fill: a division of labour. This site therefore does not document them, and
anything about _how_ a page is captured lives in
BrowserHive's documentation. Those docs are not published on the web — build
them from the BrowserHive checkout with `pnpm run docs:local`.

The interaction is **fire-and-forget**: BrowserHive answers `202` with a
`taskId` and runs the capture asynchronously on its worker pool. waggle records
which submissions were accepted and exits. Following a task to completion is not
implemented (Stage 1 of the roadmap); the outcome shows up in BrowserHive's log
and in the artifact store.
